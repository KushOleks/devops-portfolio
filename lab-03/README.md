## Завдання 1. Скрипт резервного копіювання

### Призначення

`backup.sh` — Bash-скрипт для автоматичного створення резервних копій директорій.

Скрипт створює стиснені архіви формату `.tar.gz`, додає до назв часові мітки, автоматично видаляє застарілі резервні копії та підтримує режим попереднього перегляду дій.

### Параметри

| Параметр | Призначення |
|---|---|
| `--source PATH` | Шлях до директорії, яку потрібно архівувати. Обов'язковий |
| `--dest PATH` | Директорія для збереження архівів. Обов'язковий |
| `--keep N` | Кількість останніх архівів, які потрібно залишити. Типово 5 |
| `--dry-run` | Показати заплановані дії без створення або видалення файлів |
| `--help` | Вивести довідку |

### Запуск

З кореневої директорії репозиторію:

```bash
chmod +x lab-03/backup.sh
```

Створення резервної копії:

```bash
./lab-03/backup.sh \
  --source /tmp/devops-backup-test/project \
  --dest /tmp/devops-backup-test/backups \
  --keep 3
```

Попередній перегляд:

```bash
./lab-03/backup.sh \
  --source /tmp/devops-backup-test/project \
  --dest /tmp/devops-backup-test/backups \
  --keep 3 \
  --dry-run
```

Виведення довідки:

```bash
./lab-03/backup.sh --help
```

### Пояснення `set -euo pipefail`

На початку скрипта використовується:

```bash
set -euo pipefail
```

- `-e` — зупиняє виконання, якщо команда завершується помилкою, за винятком випадків, де Bash спеціально обробляє її статус. Без цього скрипт міг би продовжити роботу після невдалого створення архіву.
- `-u` — забороняє використання неініціалізованих змінних. Без цього помилка в назві змінної могла б залишитися непоміченою.
- `pipefail` — робить конвеєр команд неуспішним, якщо будь-яка з його команд завершилася помилкою. Без нього Bash зазвичай враховує тільки статус останньої команди конвеєра.

Разом ці налаштування допомагають раніше виявляти помилки та запобігати некоректному виконанню скрипта.

### Коди виходу

| Код | Значення |
|---|---|
| `0` | Успішне виконання |
| `1` | Загальна помилка |
| `2` | Некоректні або відсутні параметри |
| `3` | Джерело не існує або недоступне |
| `4` | Помилка доступу до директорії призначення або створення архіву |

### Журналювання

Скрипт виводить час виконання, джерело, директорію призначення, кількість збережених копій, результат архівування, розмір архіву та кількість видалених копій.

Приклад:

```text
[2026-10-14 10:13:37] Source: /private/tmp/devops-backup-test/project
[2026-10-14 10:13:37] Destination: /private/tmp/devops-backup-test/backups
[2026-10-14 10:13:37] Keep: 3
[2026-10-14 10:13:37] Created: .../project-2026-10-14-101337-72965.tar.gz (522 bytes)
[2026-10-14 10:13:37] Deleted: .../project-2026-10-14-100400-66053.tar.gz
[2026-10-14 10:13:37] Result: archived=1, deleted=1, size=522 bytes
```

Журнал виводиться у стандартний потік виведення, тому за потреби його можна перенаправити у файл.

### Результати тестування

1. **Створення архіву:** створено архів `.tar.gz` розміром 522 байти.
2. **Ротація:** після шести запусків із `--keep 3` залишилися три найновіші архіви.
3. **Dry-run:** скрипт показав заплановане створення та видалення, але кількість і склад файлів не змінилися.
4. **Неіснуюче джерело:** отримано зрозуміле повідомлення про помилку та код виходу `3`.
5. **Шляхи з пробілами:** успішно створено архів `my project-...tar.gz`.
6. **Сторонні файли:** файл `important.txt` і архів іншого джерела не були видалені.
7. **Вміст архіву:** командою `tar -tzf` підтверджено наявність `project/file1.txt` та `project/file2.txt`.

### Обмеження

Скрипт призначений для локального резервного копіювання директорій. Ротація визначає належність архівів за шаблоном імені джерела та часовою міткою. Скрипт не реалізує блокування одночасних запусків, віддалене зберігання або автоматичне відновлення даних. Імена файлів із символами нового рядка не підтримуються повністю під час сортування архівів.

### Висновок

У результаті виконання завдання розроблено Bash-інструмент резервного копіювання з параметрами командного рядка, автоматичною ротацією архівів, режимом `--dry-run`, перевіркою помилок і журналюванням. Основні сценарії роботи перевірено на macOS.

## Завдання 2. Монітор доступності API

### Призначення

`api_monitor.py` — Python-скрипт для автоматизованої перевірки доступності HTTP/HTTPS endpoint-ів.

Інструмент перевіряє HTTP-коди та час відповіді, класифікує мережеві помилки, виконує повторну спробу при мережевих збоях, записує результати у JSONL-журнал і надсилає Telegram-сповіщення.

Для реалізації використовується стандартна бібліотека Python.

### Конфігурація

Список endpoint-ів зберігається у файлі `lab-03/config/endpoints.json`.

Приклад конфігурації:

```json
{
  "endpoints": [
    {
      "name": "Healthy API",
      "url": "https://httpbin.org/status/200",
      "expected_status": 200,
      "timeout": 5,
      "max_response_time": 3
    }
  ]
}
```

Параметри:

| Параметр | Призначення |
|---|---|
| `name` | Назва цілі |
| `url` | Адреса endpoint |
| `expected_status` | Очікуваний HTTP-код |
| `timeout` | Максимальний час очікування мережевої операції |
| `max_response_time` | Допустимий час відповіді |

Адреси endpoint-ів зберігаються у конфігурації, а секрети Telegram передаються через змінні середовища.

### Запуск

Довідка:

```bash
python3 lab-03/api_monitor.py --help
```

Запуск моніторингу:

```bash
python3 lab-03/api_monitor.py \
  --config lab-03/config/endpoints.json \
  --log lab-03/api-monitor-results.jsonl
```

### Типи збоїв

| Тип збою | Опис |
|---|---|
| `DNS_ERROR` | Доменне ім'я не вдалося перетворити на IP-адресу |
| `CONNECTION_REFUSED` | TCP-з'єднання було відхилене |
| `TIMEOUT` | Перевищено час очікування |
| `SSL_ERROR` | Помилка перевірки SSL/TLS-сертифіката |
| `UNEXPECTED_STATUS` | Отриманий HTTP-код не відповідає очікуваному |
| `SLOW_RESPONSE` | Час відповіді перевищив встановлений поріг |
| `NETWORK_ERROR` | Інша мережева помилка |

Для мережевих помилок виконується одна повторна спроба перед фіксацією остаточного результату.

### Telegram-сповіщення

Для надсилання сповіщень використовуються змінні середовища:

- `TELEGRAM_BOT_TOKEN` — токен Telegram-бота.
- `TELEGRAM_CHAT_ID` — ідентифікатор чату.

Приклад налаштування:

```bash
export TELEGRAM_BOT_TOKEN="your_token"
export TELEGRAM_CHAT_ID="your_chat_id"
```

Справжні токени не зберігаються в репозиторії.

Приклад отриманого повідомлення:

```text
API Monitor Alert
Target: Timeout test
Type: TIMEOUT
Details: The read operation timed out
```

### Журналювання

Результати записуються у форматі JSON Lines (`.jsonl`).

Кожен запис містить час перевірки, назву та URL цілі, статус, тип збою, HTTP-код, час відповіді й опис результату.

Приклад:

```json
{"timestamp":"2026-10-14T07:52:17.298920+00:00","name":"Timeout test","url":"https://httpbin.org/delay/5","status":"FAIL","failure_type":"TIMEOUT","http_status":null,"response_time":1.41,"message":"The read operation timed out"}
```

### Коди виходу

| Код | Значення |
|---|---|
| `0` | Усі endpoint-и успішно пройшли перевірку |
| `1` | Виявлено щонайменше один збій |
| `2` | Помилка конфігурації |

### Результати тестування

Перевірено такі сценарії:

1. Робочий endpoint — `OK`.
2. Неіснуючий домен — `DNS_ERROR`.
3. Закритий порт — `CONNECTION_REFUSED`.
4. Прострочений сертифікат — `SSL_ERROR`.
5. Неочікуваний HTTP-код — `UNEXPECTED_STATUS`.
6. Повільна відповідь — `SLOW_RESPONSE`.
7. Перевищення часу очікування — `TIMEOUT`.
8. Повторна спроба при мережевій помилці.
9. Запис результатів у JSONL.
10. Надсилання Telegram-сповіщень.

### Чим з'єднання відхилено відрізняється від тайм-ауту?

**CONNECTION_REFUSED** означає, що спроба встановити TCP-з'єднання отримала явну відмову. Це часто відбувається, коли сервер доступний, але на відповідному порту немає сервісу, що приймає з'єднання.

У такій ситуації перевіряють стан сервісу, налаштування порту та мережеві правила.

**TIMEOUT** означає, що мережева операція не завершилася протягом відведеного часу. Причинами можуть бути проблеми мережі, втрата пакетів, перевантаження сервера або зависання обробки запиту.

У цьому випадку перевіряють мережевий маршрут, затримки, навантаження та час обробки запитів.

Таким чином, ці типи збоїв вимагають різних діагностичних дій.

### Висновок

Розроблено інструмент моніторингу API, який перевіряє доступність endpoint-ів, визначає конкретні причини збоїв, підтримує повторні спроби, структуроване журналювання та Telegram-сповіщення. Функціональність перевірено на тестових сценаріях.



## Завдання 3. Інтеграція з Git (Git Hooks)

### Мета завдання

Реалізувати два Git-хуки для автоматичної перевірки якості коду перед створенням комітів і відправленням змін до віддаленого репозиторію.

Реалізовано:
- `pre-commit` — перевірка лише файлів, доданих до індексу Git (staged files), за допомогою лінтерів.
- `pre-push` — автоматичний запуск тестів перед відправленням змін на GitHub.

Якщо перевірка завершується помилкою, відповідна Git-операція блокується.

### Структура файлів

```text
lab-03/
├── hooks/
│   ├── pre-commit
│   └── pre-push
└── tests/
    └── test_backup.py
```

### Встановлення Git-хуків

Git не встановлює автоматично хуки, які зберігаються у звичайних папках репозиторію.

Для їх активації необхідно виконати з кореневої папки проєкту:

```bash
chmod +x lab-03/hooks/pre-commit
chmod +x lab-03/hooks/pre-push
git config --local core.hooksPath lab-03/hooks
```

Перевірка налаштування:

```bash
git config --local --get core.hooksPath
```

Очікуваний результат:

```text
lab-03/hooks
```

Для роботи хуків необхідні:
- Python 3 — для запуску автоматичних тестів.
- ShellCheck — для перевірки Bash-скриптів.
- Ruff — для перевірки Python-коду.

Встановлення лінтерів на macOS:

```bash
brew install shellcheck ruff
```

### Хук pre-commit

Хук `pre-commit` автоматично запускається перед створенням кожного коміту.

Для отримання списку файлів використовується команда:

```bash
git diff --cached --name-only --diff-filter=ACMR -z
```

Вона повертає лише файли, підготовлені до коміту.

Залежно від розширення файлу запускається відповідний лінтер:
- `*.sh` — ShellCheck.
- `*.py` — Ruff.

Команда `git show :<шлях_до_файлу>` дозволяє перевіряти саме ту версію файлу, яка додана до індексу Git, а не незбережені для коміту зміни робочої директорії.

Якщо лінтер виявляє помилку, хук повертає ненульовий код завершення, і Git блокує створення коміту.

### Хук pre-push

Хук `pre-push` автоматично запускається перед відправленням змін до віддаленого репозиторію.

Він виконує команду:

```bash
python3 -m unittest discover -s lab-03/tests -p "test_*.py" -v
```

Ця команда запускає автоматичні тести з папки `lab-03/tests`.

Для скрипту резервного копіювання `backup.sh` реалізовано чотири тести:

1. Перевірка успішного створення архіву та наявності файлу всередині нього.
2. Перевірка режиму `--dry-run`, за якого архів не створюється.
3. Перевірка обробки помилки, якщо вихідна директорія не існує.
4. Перевірка створення архіву з параметром `--keep 1`.

Якщо хоча б один тест завершується невдало, `pre-push` повертає ненульовий код завершення, що блокує виконання `git push`.

### Перевірка роботи хуків

**Перевірка pre-commit**

Для тестування створено тимчасовий Bash-файл із синтаксичною помилкою — відсутнім оператором `fi`.

ShellCheck виявив помилки `SC1046`, `SC1047`, `SC1072`, `SC1073`.

Хук завершився повідомленням:

```text
ERROR: Lint checks failed. Commit blocked.
```

Коміт не було створено.

**Перевірка pre-push**

Спочатку запущено чотири автоматичні тести. Усі завершилися успішно:

```text
Ran 4 tests

OK
Pre-push tests passed.
```

Після цього тимчасово додано тест із навмисною помилкою:

```python
self.assertEqual(1, 2)
```

У результаті отримано:

```text
Ran 5 tests

FAILED (failures=1)
ERROR: Tests failed. Push blocked.
```

Після видалення помилкового тесту всі чотири перевірки знову пройшли успішно.

### Чому Git-хуки не є механізмом примусового контролю?

Git-хуки працюють локально на комп'ютері розробника.

Вони не встановлюються автоматично під час клонування репозиторію. Кожен розробник може самостійно змінити, видалити або вимкнути їх.

Крім того, хуки можна обійти за допомогою параметра `--no-verify`:

```bash
git commit --no-verify
git push --no-verify
```

Тому Git-хуки допомагають виявляти помилки на ранніх етапах розробки, але не гарантують дотримання правил усіма учасниками команди.

### Що забезпечують обов'язкові перевірки в CI, чого не забезпечують Git-хуки?

CI (Continuous Integration) — це процес автоматизованої перевірки коду в централізованому середовищі, наприклад GitHub Actions.

На відміну від локальних Git-хуків, CI дозволяє:

1. Запускати перевірки незалежно від налаштувань комп'ютера розробника.
2. Автоматично перевіряти код під час створення Pull Request.
3. Відображати результати перевірок усім учасникам команди.
4. Налаштовувати обов'язкові перевірки (required status checks).
5. Забороняти злиття Pull Request у захищену гілку, доки необхідні перевірки не завершаться успішно.

Отже, Git-хуки забезпечують швидку локальну перевірку коду, а CI разом із правилами захисту гілок дозволяє централізовано контролювати якість змін.

### Висновок

У ході виконання завдання реалізовано два Git-хуки: `pre-commit` і `pre-push`.

Перший автоматично перевіряє лише підготовлені до коміту Bash- та Python-файли за допомогою ShellCheck і Ruff. Другий запускає автоматичні тести перед відправленням змін до віддаленого репозиторію.

Роботу обох хуків перевірено на успішних і помилкових сценаріях. Також розглянуто обмеження локальних Git-хуків і переваги обов'язкових перевірок у CI.



## Бонус 1. Скрипт моніторингу системи

### Мета завдання

Розробити Bash-скрипт для автоматичного моніторингу системних ресурсів, виявлення перевищення встановлених порогів та запису попереджень до журналу.

### Реалізовані можливості

Створено скрипт `monitor.sh`, який перевіряє:

- завантаження процесора (CPU);
- використання оперативної пам'яті (RAM);
- відсоток вільного місця на диску;
- стан заданих процесів.

Скрипт підтримує macOS та Linux.

Пороги задаються окремо у файлі `config/monitor.conf`, а не безпосередньо в коді.

### Конфігурація

Приклад конфігураційного файлу:

```bash
CPU_THRESHOLD=90
MEMORY_THRESHOLD=90
DISK_FREE_THRESHOLD=10
MONITOR_PROCESSES="Finder"
LOG_FILE="$HOME/devops-monitor.log"
```

Параметри:

- `CPU_THRESHOLD` — максимально допустиме використання CPU у відсотках.
- `MEMORY_THRESHOLD` — максимально допустиме використання RAM у відсотках.
- `DISK_FREE_THRESHOLD` — мінімально допустимий відсоток вільного місця.
- `MONITOR_PROCESSES` — перелік процесів для перевірки.
- `LOG_FILE` — шлях до журналу попереджень.
- `DISK_PATH` — шлях до файлової системи, яку потрібно перевіряти; за замовчуванням використовується домашня директорія.

Інший конфігураційний файл можна вибрати через змінну `MONITOR_CONFIG`.

### Запуск скрипту

```bash
chmod +x lab-03/monitor.sh
./lab-03/monitor.sh
echo "Exit code: $?"
```

Коди завершення:

- `0` — усі показники в межах установлених порогів.
- `1` — виявлено хоча б одне попередження.
- `2` — помилка конфігурації або отримання системних показників.

Кожен рядок виводу містить дату, час, рівень повідомлення, назву показника, значення та пояснення.

### Перевірка спрацювання порогів

Для тестування створено тимчасову конфігурацію зі зниженими порогами:

```bash
cp lab-03/config/monitor.conf /tmp/devops-monitor-test.conf
sed -i '' 's/CPU_THRESHOLD=90/CPU_THRESHOLD=1/' /tmp/devops-monitor-test.conf
sed -i '' 's/MEMORY_THRESHOLD=90/MEMORY_THRESHOLD=1/' /tmp/devops-monitor-test.conf
MONITOR_CONFIG=/tmp/devops-monitor-test.conf ./lab-03/monitor.sh
```

Отримано попередження про перевищення порогів CPU та RAM.

Також перевірено відсутність заданого процесу. Скрипт вивів попередження `PROCESS` і завершився з кодом `1`.

### Журналювання

Попередження та помилки автоматично записуються до журналу:

```bash
tail -n 20 ~/devops-monitor.log
```

Кожен запис містить часову позначку та причину спрацювання.

### Автоматичний запуск через cron

Для тестування налаштовано запуск щохвилини:

```cron
* * * * * /bin/bash /Users/mac/devops-portfolio/lab-03/monitor.sh >> /Users/mac/devops-cron.log 2>&1
```

Перевірка журналу автоматичних запусків:

```bash
tail -n 20 ~/devops-cron.log
```

У журналі зафіксовано успішні запуски о 08:44, 08:45, 08:46 та 08:47.

Під час початкового тестування виникла помилка `sysctl: command not found`, пов'язана з обмеженою змінною `PATH` у середовищі `cron`.

Проблему усунуто додаванням системних шляхів до `PATH` у скрипті.

Після перевірки щохвилинний запуск було вимкнено.

### Висновок

У ході виконання бонусного завдання створено скрипт моніторингу системи, який перевіряє процесор, оперативну пам'ять, вільне місце на диску та стан процесів.

Реалізовано конфігуровані пороги, журналювання попереджень, ненульові коди завершення та можливість автоматичного запуску через `cron`.

Працездатність перевірено шляхом штучного заниження порогів, перевірки відсутнього процесу та аналізу журналів кількох автоматичних запусків.


## Бонус 2. Аналізатор журналів вебсервера

### Мета роботи

Розробити Python-програму для аналізу журналів вебсервера у форматі Combined Log Format, визначення найактивніших IP-адрес, розподілу HTTP-статусів та годин пікового навантаження.

### Реалізація

Створено програму `log_analyzer.py`, яка:

- читає журнал вебсервера;
- розбирає записи у форматі Combined Log Format;
- визначає топ-N IP-адрес за кількістю запитів;
- групує HTTP-статуси за класами 1xx, 2xx, 3xx, 4xx та 5xx;
- підраховує кількість запитів за годинами;
- визначає години пікового навантаження;
- пропускає пошкоджені записи та підраховує їхню кількість;
- формує текстовий або JSON-звіт.

Для реалізації використано стандартні бібліотеки Python: `argparse`, `re`, `datetime`, `collections`, `json` та `pathlib`.

### Структура файлів

- `log_analyzer.py` — основна програма.
- `samples/access.log` — тестовий журнал вебсервера.
- `tests/test_log_analyzer.py` — автоматичні тести.

### Параметри командного рядка

- `--input` — шлях до вхідного журналу.
- `--output` — шлях до вихідного звіту.
- `--format` — формат звіту (`text` або `json`).
- `--top` — кількість IP-адрес у рейтингу.

### Запуск програми

Створення текстового звіту:

```bash
python3 lab-03/log_analyzer.py \
  --input lab-03/samples/access.log \
  --output /tmp/devops-access-report.txt \
  --format text \
  --top 5
```

Створення JSON-звіту:

```bash
python3 lab-03/log_analyzer.py \
  --input lab-03/samples/access.log \
  --output /tmp/devops-access-report.json \
  --format json \
  --top 3
```

### Результати тестування

Для перевірки створено журнал із 17 рядків, серед яких 14 коректних і 3 пошкоджених.

Отримано такі результати:

- Найактивніша IP-адреса: `192.168.1.10` — 6 запитів.
- HTTP 2xx — 8 запитів.
- HTTP 3xx — 2 запити.
- HTTP 4xx — 2 запити.
- HTTP 5xx — 2 запити.
- Пікова година — 09:00, 6 запитів.
- Пошкоджених записів — 3.

Пошкоджені записи не спричиняють аварійного завершення програми та не впливають на статистику коректних запитів.

### Автоматичне тестування

Реалізовано 6 тестів, які перевіряють:

1. Розбір коректного запису.
2. Обробку пошкодженого запису.
3. Виявлення некоректної дати.
4. Виявлення неправильного HTTP-статусу.
5. Підрахунок статистики за журналом із пошкодженими рядками.
6. Формування текстового звіту.

Команда запуску:

```bash
python3 -m unittest discover -s lab-03/tests -p "test_*.py" -v
```

Усі 10 тестів лабораторної роботи виконуються успішно: 4 тести резервного копіювання та 6 тестів аналізатора журналів.

Також перевірено Git-хук `pre-push`, який автоматично запускає ці тести перед відправленням змін на GitHub.

### Висновок

У ході виконання бонусного завдання розроблено аналізатор журналів вебсервера мовою Python.

Програма визначає найактивніші IP-адреси, розподіл HTTP-статусів і години пікового навантаження, підтримує текстовий та JSON-формати звітів і коректно обробляє пошкоджені записи.

Працездатність підтверджено автоматичними тестами.


## Бонус 3. Організатор файлів на Go

### Мета

Розробити консольну утиліту на компільованій мові Go, яка автоматично організовує файли за типами, підтримує підкоманди, параметри командного рядка та режим `--dry-run`.

Додатково створити аналог на Python і порівняти розмір програм та час запуску.

### Реалізація

Файли розташовані в каталозі `lab-03/file-organizer/`:

- `main.go` — основна програма на Go.
- `main_test.go` — автоматичні тести.
- `go.mod` — опис Go-модуля.
- `organizer.py` — аналогічна реалізація на Python.
- `.gitignore` — виключення скомпільованих файлів із Git.

Програма розподіляє файли за категоріями:

- `Documents` — документи.
- `Images` — зображення.
- `Videos` — відеофайли.
- `Archives` — архіви.
- `Other` — інші типи файлів.

Підтримуються дві підкоманди:

- `list` — перегляд файлів та визначених категорій.
- `organize` — переміщення файлів у відповідні каталоги.

Параметр `--source` задає папку для обробки.

Параметр `--dry-run` дозволяє попередньо переглянути дії без фактичного переміщення файлів.

Програма не обробляє вкладені каталоги та перевіряє наявність файлу призначення, щоб уникнути перезапису.

### Збірка та запуск Go

Перейти в каталог:

```bash
cd lab-03/file-organizer
```

Зібрати програму:

```bash
go build -o file-organizer .
```

Переглянути файли:

```bash
./file-organizer list --source /tmp/devops-organizer-test
```

Перевірити переміщення без змін:

```bash
./file-organizer organize --source /tmp/devops-organizer-test --dry-run
```

Виконати сортування:

```bash
./file-organizer organize --source /tmp/devops-organizer-test
```

### Статична збірка для Linux

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w" -o file-organizer-linux-amd64 .
```

Перевірка:

```bash
file file-organizer-linux-amd64
```

Результат: виконуваний ELF-файл архітектури x86-64 зі статичним компонуванням (`statically linked`).

Розмір: приблизно 1,7 МБ.

### Автоматичне тестування

```bash
gofmt -w main.go main_test.go
go vet ./...
go test -v ./...
```

Усі 6 основних тестів пройдено успішно.

Перевірено:

1. Визначення категорії файлу.
2. Роботу підкоманди `list`.
3. Режим `--dry-run`.
4. Переміщення файлів за категоріями.
5. Захист від перезапису наявних файлів.
6. Обробку порожньої папки.

### Python-аналог

Запуск:

```bash
python3 organizer.py list --source /tmp/devops-organizer-test
```

Перевірка без переміщення:

```bash
python3 organizer.py organize --source /tmp/devops-organizer-test --dry-run
```

Сортування:

```bash
python3 organizer.py organize --source /tmp/devops-organizer-test
```

Перевірка якості коду:

```bash
ruff check organizer.py
```

### Порівняння Go та Python

Вимірювання виконано на macOS ARM64 (Apple Silicon).

Для кожної реалізації проведено 100 запусків команди `list`. Час вимірювався за допомогою Python `time.perf_counter()` та `subprocess.run()`.

| Показник | Go | Python |
|---|---:|---:|
| Середній час запуску | 4,326 мс | 27,370 мс |
| Медіана | 2,753 мс | 26,797 мс |
| Мінімальний час | 2,491 мс | 26,121 мс |
| Розмір файлу | 1,6 МБ | 2,5 КБ |

Додатково створено статичний Linux-бінарник Go розміром приблизно 1,7 МБ.

У проведеному тесті середній час запуску Go виявився приблизно у 6,3 раза меншим, ніж Python.

Результати характеризують запуск процесу та виконання команди `list` у конкретному середовищі, а не загальну швидкодію мов програмування.

### Висновок

Компіляція Go дозволяє отримати окремий виконуваний файл, який не потребує встановлення Python. Це зручно для поширення утиліт, автоматизації та запуску в серверних середовищах.

Go доцільно використовувати, коли важливі швидкий запуск, розгортання без інтерпретатора та створення самостійного виконуваного файлу.

Python зручніший для невеликих сценаріїв автоматизації, швидкого прототипування та задач, у яких важливі простота розробки й можливість швидко змінювати код.

Під час виконання роботи реалізовано дві версії організатора файлів, перевірено їхню функціональність, створено статичну збірку Go та проведено експериментальне порівняння часу запуску й розмірів файлів.
